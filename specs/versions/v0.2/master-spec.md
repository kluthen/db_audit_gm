# db_audit_gm v0.2 — Master specification

Status: consolidated on 2026-10-21 after an independent review of the
drafts (verdict: no blocking issue); **awaiting the owner's approval**.
Companion: [access-model.md](access-model.md).
Baseline: the released [v0.1 master spec](../v0.1/master-spec.md) and its
[access model](../v0.1/access-model.md). Everything v0.1 specifies stays
in force unless this document changes it; where they disagree, this
document wins for v0.2.

---

## 1. Concept and objective

db_audit_gm generates live database audit exercises: an agent, the game
master (GM), deploys a deliberately flawed data stack on a container
cluster, hands it to students (the players) through a single bastion,
receives their report and gives teacher-style feedback. v0.1 settled the
GM's stance on one static PostgreSQL database.

v0.2 adds **monitoring and the usual tooling**. In the owner's words:
"We will first bundle a few bricks with the most common (free,
open-source) monitoring tools: some Grafana dashboard, some system
monitoring tool (docker up and down, load, etc.), eventually log
aggregators." Concretely:

1. **One free default tool per need**, chosen with footprint on a
   2 CPU / 4G RAM / 8G disk laptop as a main criterion: per-node health,
   PostgreSQL metrics, a metrics store, dashboards and alerting, log
   analysis. The owner's own reference setup (`~/audits/bluebox-lab`) is
   the model; the gap it leaves, a general per-node health view (CPU,
   RAM, disk, services), is what v0.2 fills.
2. **Monitoring is something to audit.** Monitoring bricks are optional
   in a topology, may be ill-configured, miss nodes or be starved of
   information, and how well the customer is tooled is itself a finding:
   tooling should be proportionate to the topology.
3. **One new scenario**, partly tooled, with monitoring faults mixed with
   database faults, while the v0.1 scenario keeps passing.

## 2. Scope

### In scope

- New bricks: `prometheus` (metrics store, which also ships the
  node-health script), `postgres-exporter`, `grafana` (dashboards and
  alerting). Each is a full node of its own.
- Changed bricks: `postgres` (file logging read by pgBadger,
  `pg_stat_statements`) and `bastion` (a web front publishing the
  monitoring interfaces), both moving from 0.1.1 to 0.2.0.
- Format changes: the GM documentation every brick ships, footprints in
  limits and reservations, companion material the GM mounts into other
  nodes, parameter-planted faults, where evidence is run, tooling
  expectations, version rules.
- Script changes: capacity check counting images, network naming,
  secrets generated by kind, mounted material, parameter faults.
- One new scenario; `bookshop-new-server` re-pinned to the changed
  bricks as the v0.1 regression.
- Times in UTC everywhere.

### Out of scope (deferred, still part of the project)

- Producers, consumers and any load: the database stays static, so
  monitoring watches a quiet system; monitoring faults that only show
  under load. Load arrives with producers and consumers (v0.3).
- A log aggregator, a separate alerting brick, cAdvisor, any Docker
  socket or host mount.
- Other tools and other health solutions (Nagios and the like),
  hand-made scripts as customer tooling, pgwatch, pgCluu, VictoriaMetrics
  (v0.5).
- The bastion as the players' main activity point: a documentation
  website, general-use tooling, reports published on the bastion (v0.6).
- Backup tooling and its fault families: no version has been chosen yet.
- Network faults, a second network, multi-host swarms and an image
  registry; aging; a deliberate pair of faults where one masks the other.
- Notification channels for alerts; HTTPS on the web front.

## 3. Actors

Unchanged from v0.1: the initiator, the players, the GM, anyone in the GM
session, and the unauthenticated network visitor. v0.2 gives the players
a second per-game credential, the tools password, and three more nodes
to reach. The full rules are in the access model.

## 4. Glossary (additions and changes)

| Term | Meaning |
|---|---|
| Brick | A reusable node definition in the catalog: image, configuration, GM and player documentation, validator, companion material. It no longer lists the faults it hosts: each fault's `applies_to` alone says that |
| GM documentation | A brick's `docs/gm.md`, nine required sections, never shipped to players |
| Metrics store | The node that collects metrics: the `prometheus` node in v0.2 |
| Node-health script | A daemon script, companion material of `prometheus`, mounted into every node, reporting the node's CPU, memory, disk and services |
| Mounted companion material | Files a brick ships that the GM mounts as configs into other nodes at deploy |
| Receiving brick | A brick whose nodes receive another brick's mounted material |
| Web front | The bastion's reverse proxy publishing every monitoring web interface on its second port |
| Tools password | The per-game password that opens the web front and Grafana's administrator account |
| Tooling expectation | An answer-key item saying what monitoring the GM silently expects of the customer and what is acceptable; not a fault |
| Parameter fault | A fault planted by changing a parameter of its target node when the local implementation is rendered |

## 6. Format changes

### 6.1 `brick.yaml`

- **Footprint** takes the shape of a scenario node's `resources`: limits
  for CPU and memory, reservations for CPU, memory and disk. It is the
  default the GM starts from when it sizes a scenario; the capacity check
  and the renderer read the scenario's own `resources`. A brick's own
  footprint excludes any material other bricks mount into it.
- **No fault list.** `compatible_faults` is gone; which faults a brick
  hosts is stated only by each fault's `applies_to`.
- **Mounted companion material.** A brick may ship companion material
  the GM mounts into other nodes at deploy, as read-only configs. For
  each such item the companion declaration states: the files, each with
  its target path and mode in the receiving node (root-owned, read-only,
  so a protected file); which nodes receive it (those the brick's
  parameter for it lists); the parameter that configures it per node,
  set on the brick's own node in the scenario; what it adds to each
  receiving node's footprint; and what a receiving image must provide
  (by name: the s6-overlay version, the commands used).
- **Receiving bricks** declare what they provide to mounted material
  (their s6-overlay version, the commands available). The loader checks
  each receiving node's declaration against the requirements of the
  mounting brick's pinned version, and refuses a topology where one is
  not met.

### 6.2 `docs/gm.md`: nine required sections

Every brick ships GM documentation telling the GM what to install where,
how to configure it and wire it to other bricks, what it costs, which
faults it hosts and how to check it. `brick.yaml` declares, `docs/gm.md`
explains. The format skill refuses a brick that lacks a section, so the
GM refuses to deploy a scenario using it. The v0.1 bricks already meet
this at 0.1.1.

Rules: one level-2 heading per section, with these exact names, in this
order; a brick may add its own sections as subsections or after the
last. No section is empty; one that does not apply says so and why. The
file agrees with `brick.yaml` (every parameter, knob, interface or
footprint figure it mentions matches, and it introduces none that
`brick.yaml` lacks) and with the catalog faults' `applies_to` (every
fault it lists names this brick and version, and every catalog fault
that does is listed). A disagreement is a defect of the brick. Placement
and connections are stated as requirements, never in a platform's own
syntax.

1. **Purpose**: the technology, version and image; the roles it fills;
   when the GM picks it.
2. **Placement**: what gets installed (a node of its own, and any
   companion material the GM mounts into other nodes), how to build it,
   how many per scenario, next to which node, whether it is stateful,
   which networks it joins.
3. **Configuration**: every parameter the scenario sets and every value
   the GM sets per scenario or per node (mounted material's per-node
   values included), each with its meaning, default, valid values and
   where it lands; knobs and envelopes; secrets and seed files; what
   start-up does.
4. **Connections**: for each interface provided or consumed, the bricks
   on the other side, port and protocol, what the GM wires and where, the
   account the other side must provide, what must exist first; what it
   exposes to monitoring; whether its image accepts another brick's
   mounted material.
5. **Access**: how the player reaches it (account, group, `sudo`
   wrappers, any web interface and its path through the bastion),
   writable and protected paths, write policies, capabilities added back
   and why, what the GM uses to operate it.
6. **Footprint**: default limits and reservations as `brick.yaml`
   declares them; what makes it grow; how the GM sizes it; what its
   mounted material adds to each node it lands on; the levers that
   shrink it.
7. **Supported faults**: the catalog faults whose `applies_to` names
   this brick and version, and what each needs from it. Catalog faults
   only: a fault defined in a scenario's own `faults/` folder is the
   scenario's and is not listed. Then faults it lends itself to without a
   definition yet, its known interactions, and faults it cannot host.
8. **Checks**: its validator, health check, companion checks and when to
   run them, how the GM confirms after deployment that it works and is
   wired (every scrape target up, the exporter connected), its stack
   test if any.
9. **Known limits**: what it does not do, or does surprisingly; "none
   known" when so.

### 6.3 Scenario and answer key

- **Where evidence is run.** Each evidence entry in an answer key has a
  required `where`: `bastion`, `node:<name>`, `ui:<name>` (an interface
  the web front publishes) or `report:<tool>` (a generated report, such
  as pgBadger's). `bookshop-new-server`'s key gains it at its re-pin.
- **Tooling expectations.** The answer key holds a list of the GM's
  silent tooling expectations, apart from the fault instances: each says
  what is expected and what is acceptable (any of the top three tools for
  a need, for example), has no sealed check, and is judged in feedback.
  An issue may cover a tooling expectation as well as faults.
  Under-tooling and overkill (tooling needing about three times the
  compute and disk of what it watches) are findings, never a fault kind.
  The bastion and its tools are the players' kit and do not count as the
  customer's tooling.
- **Networks.** Each network a scenario declares renders as one network
  named `<game_id>_<network name>` (v0.1 rendered a single
  `<game_id>_net`). v0.2 scenarios declare one network.

### 6.4 Fault definition

- **`applies_to` lists brick versions one by one**, never as ranges, so
  a fault never claims a brick version nobody tried it on; each brick
  bump adds the new version to every fault that still applies.
- **A new injection kind, `parameter`**, beside `seed-file` and `state`:
  a change to a parameter of the target node, applied when the local
  implementation is rendered. The loader validates it as it validates
  seed changes today.
- **Faults about mounted material** target the node of the brick that
  ships it, name only that brick in `applies_to`, and take the affected
  node as a parameter. For the node-health script: the target is the
  `prometheus` node, and the fault is planted through its service map
  (a node left out of it, or a service left out of a node's entry).

### 6.5 Versions and pins

- Any change to a brick bumps its version, whatever part of its folder
  changes (image, `brick.yaml`, validator, documentation, companion
  material), even with a byte-identical image. Changes made while a new
  version is unreleased (its branch not merged into `main`) fold into it.
- `postgres` and `bastion` were released at 0.1.1; v0.2's changes to
  them take **0.2.0**. New bricks start at **0.1.0**.
- **Faults and scenarios never bump.** They keep their version whatever
  changes; git history is the record. A pin to a fault names the fault,
  not a state of it; nothing pins a scenario.
- The node-health script has no version of its own: it is versioned with
  `prometheus`, and any change to it bumps `prometheus`.

## 7. The bricks

Every new brick is a **full node**: `sshd` and the `player` account
reached from the bastion, s6-overlay, a read-only root, a public
validator, the seed-once entrypoint copying the scenario's seed files
into an editable volume on first start, capabilities dropped and added
back as listed, *fixable* or *report-only* per scenario, configuration
reloaded through `sudo` wrappers. Prometheus and Grafana keep separate
nodes whatever the measured footprint. No node other than the bastion
publishes a port.

### 7.1 The node-health script (companion of `prometheus`)

- A daemon reporting, from inside its node: CPU and memory from the
  node's own cgroup v2 files; disk as the use of the node's own volumes
  (`du`) against the node's declared disk reservation; and the status of
  the node's important services through `s6-svstat`. It serves them in
  Prometheus' text format on a fixed port, through a minimal listener,
  readable from every node of the game, the bastion included. The health
  view shows the host's free space once, not per node, since on one host
  every node sees the same figure.
- No Docker socket, no host mount, no cAdvisor: the player side stays
  free of anything that reaches the engine.
- **Delivery.** The GM installs it at deploy: the script and its s6
  service are mounted into each node as configs, so no image carries it
  and an image only has to accept a mounted service (s6-overlay v3, both
  v0.1 bricks already run it, and the commands the script uses). Every
  `debian:13-slim` image has `perl-base` and its socket module, enough
  for the listener. The script and listener run as an unprivileged
  account, not root, provided `s6-svstat` can read the services' status
  as that account (section 15).
- **Where.** On every node whenever the topology has a `prometheus`
  node, that node included; nowhere otherwise. A node left out is a
  monitoring fault.
- **Configuration.** A parameter of the `prometheus` node: a map that
  lists every node of the topology by name, each entry a list of
  services or `default` (that node's brick's s6 processes). The map is
  required with a `prometheus` node, and the format skill and loader
  refuse a missing map or a missing node; leaving a node out exists only
  as a parameter fault. The renderer writes each node's entry, with the
  node's disk reservation, into that node's own config.
- **Read-only on the node.** A wrong service list or a left-out node can
  be reported, or a fix proposed, but no player can fix it.
- **Its runtime cost counts against each node's own limits**, the
  nerfed database's included (about 5M of memory and 0.005 CPU). The
  scenario's per-node `resources` include it; bricks' own footprints do
  not, and `prometheus`'s GM documentation states what it adds per node.
- **Documentation**: in `prometheus`'s `docs/gm.md`: Placement covers
  mounting it into the other nodes, Configuration the service map,
  Footprint its per-node cost, Supported faults the faults about it.
  Each receiving brick's `docs/gm.md` says under Connections that its
  image accepts it.
- A later metrics store other than Prometheus would need its own copy.

### 7.2 `prometheus`

- Prometheus on its own node. Its scrape targets (the exporter, every
  node's health endpoint) live in its seed configuration, so a node left
  out of the targets is a plantable fault. Retention is bounded both by
  time and by size, about a day.
- Configuration is reloaded through a `sudo` wrapper on a fixable node;
  Prometheus' admin and lifecycle HTTP endpoints stay disabled.
  Prometheus has no login of its own; its UI is reached through the web
  front.

### 7.3 `postgres-exporter`

- `postgres_exporter` on its own node, connecting to the database with a
  monitoring role that holds `pg_monitor`. The role's password is a
  per-game secret generated at deploy, readable on the exporter node by
  the exporter's account only.

### 7.4 `grafana`

- Grafana with its own alerting; there is no separate alerting brick.
  Data sources, dashboards and alert rules are provisioned from seed
  files the player can edit on a fixable node. There is no notification
  channel: firing alerts are read in Grafana's alerting view. Grafana's
  default time zone is UTC.
- The administrator account's password is the per-game tools password,
  always: there is no default-password fault.
- Because the tools password makes the players Grafana administrators,
  they can change dashboards, data sources and alert rules through the
  UI even on a report-only Grafana node. This is accepted (access model,
  "Known gaps"). Sealed checks on Grafana judge its effective live state,
  through its API, not only the provisioned files.

### 7.5 `postgres` 0.2.0

- PostgreSQL logs to files on a log volume, rotated by size, with a
  `log_line_prefix` pgBadger parses and `log_timezone = UTC`. The logging
  settings live in the seed `postgresql.conf`, so faults can live there.
  The log files are readable by the players' group.
- pgBadger is installed in the image. The players run it themselves, as
  `player`, as a one-shot job against the log files, with no wrapper; its
  HTML report lands in their home on the node, and they copy it out with
  `scp` to the bastion and `sftp` from there.
- `pg_stat_statements` is available, its preloading set in the seed
  configuration, so its absence can be a fault.
- With file logging, the PostgreSQL log leaves Docker's service logs:
  `gmctl logs` shows only the start-up, and the GM reads the file log
  through the exec operation.
- A pgBadger run uses the database node's own limits: a large run could
  take memory from PostgreSQL (measured, section 14).

### 7.6 `bastion` 0.2.0

- A **web front**: a reverse proxy (about 10–20M of memory) on the
  bastion's second published port, in host mode, default 8080 (the local
  implementation records the port actually used), every monitoring
  interface behind it under its own path, HTTP basic authentication on
  the tools password, plain HTTP. A request without the password is
  refused with HTTP 401.
- The game publishes exactly two ports, both on the bastion: SSH and the
  web front.

## 8. Content delivery, the local implementation and the scripts

- **Capacity check.** `gmctl fit` also counts the images' sizes against
  the declared disk, since on a laptop the images grow, not the volumes.
  One host remains the only playground shape.
- **Networks** render as section 6.3 says.
- **Secrets.** `gmctl deploy` generates the secrets the bricks declare,
  by kind (password, key pair), instead of its fixed four. New per-game
  secrets: the tools password and the monitoring role's password. Both
  are kept in the local implementation's `secrets/` folder (mode 0600)
  with the others, so a restarted GM can hand them over again.
- **Mounted material.** The renderer adds the mounting brick's configs to
  every receiving node's service, from the parameter's per-node entries.
- **Parameter faults** are applied by the renderer when it writes the
  local implementation, before deployment.
- **Times.** Nodes run with `TZ=UTC`.

## 9. The game in v0.2

The stages of v0.1 stand, with these changes:

- **Deployment** mounts the node-health script into every node when the
  topology has a `prometheus` node.
- **No aging**: with no load, history builds during the game, and the
  dashboards' first 10 to 15 minutes are thin.
- **Hand-over** adds the tools password and the web front's address and
  port to the bastion's.
- **Times**: the GM states every time in UTC, as the nodes, PostgreSQL's
  logs and Grafana do.
- **Feedback** also covers the GM's tooling expectations, where the
  answer key lists any, beside the faults present.

## 10. Player access and rules

The full rules are in the access model. In short: everything is reached
through the bastion only, by SSH (the nodes) and through the web front
(the interfaces); players read every node and change configuration on
fixable nodes through their `sudo` wrappers; the node-health script and
its list are read-only everywhere; they run pgBadger themselves on the
database node; and two gaps are accepted under light enforcement: a
PostgreSQL superuser can still run `ALTER SYSTEM` on a report-only
database node, and a Grafana administrator can still edit Grafana's
content on a report-only Grafana node.

## 11. The v0.2 scenarios and faults

### 11.1 The new scenario

- One new, partly tooled scenario with one database, for a small or
  mid-size customer: some monitoring present and ill-configured, one need
  left uncovered as an under-tooling issue or tooling expectation. Not an
  HA customer (that implies a standby), and no second, reporting
  database.
- **Faults**: four to six monitoring faults, all visible without load, at
  least one of them a tool starved of information, mixed with database
  faults from v0.1's families. The under-tooling item is not a fault.
  Candidates, to be chosen when the folder is written:
  - a node missing from Prometheus' scrape targets, with no alert on a
    target down;
  - a node left without the node-health script;
  - a node-health service list leaving out the node's main service, so
    the node shows healthy while its database is down;
  - no slow-query log (`log_min_duration_statement = -1`), a
    `log_line_prefix` pgBadger cannot parse, or non-English
    `lc_messages`;
  - `pg_stat_statements` not preloaded, so the query panels are empty;
  - the exporter's role without `pg_monitor`, so panels are partial;
  - a Grafana data source pointed at the wrong address;
  - an alert threshold in the wrong unit, or a `for:` longer than the
    incident;
  - retention shorter than the dashboards' or alerts' window.
- The two node-health faults are *report* or *propose* issues, never
  *fix*, since their material is read-only on the node.
- The owner reviews the chosen faults, issues, expectations and answer
  key before the scenario is accepted.

### 11.2 `bookshop-new-server`

Re-pinned to `postgres` and `bastion` 0.2.0, keeping its version; its
answer key gains `where` on every evidence entry. It must still pass its
v0.1 checks.

## 12. Footprint and capacity

Estimates, not measurements: nothing in v0.1 or the reference setup
sizes these services. Per node, as a scenario's `resources` (so each
includes its `sshd`, s6 and node-health script), for about five nodes, a
few thousand series and a static database:

| Node | Reservation CPU | Reservation memory | Volumes | Limit CPU | Limit memory |
|---|---|---|---|---|---|
| `bastion`, with web front | 0.1 | 96M | 256M | 0.5 | 256M |
| `db`, with log volume | 0.5 | 512M | 2.25G | 1 | 1G |
| `prometheus` | 0.1 | 160M | 512M | 0.5 | 384M |
| `grafana` | 0.1 | 160M | 256M | 0.5 | 384M |
| `postgres-exporter` | 0.05 | 48M | 64M | 0.25 | 128M |
| **Total** | **0.85** | **976M** | **3.3G** | | |

- Against the `laptop` playground (2 CPU / 4G / 8G) with the capacity
  check's 10 % headroom, about 47 % of the usable CPU, 26 % of the memory
  and 46 % of the disk are reserved. CPU is the tightest dimension.
- Images: about 0.8G more than v0.1's 0.44G (Grafana about 450M,
  Prometheus about 150M, the exporter about 25M, pgBadger and its Perl
  modules about 30M, and about 40M of system layer per new image over
  the shared `debian:13-slim` layer). Volumes plus images: about 4.5G of
  8G.
- At rest (estimate): Prometheus 80–150M, Grafana 100–150M, the exporter
  15–30M. Peaks: a pgBadger run within the database node's 1G limit, a
  dashboard load within Grafana's 0.5 CPU.
- Proportion: the tooling reserves between a third and three quarters of
  what the database does, well under the overkill yardstick for a
  one-database customer.
- Levers if measurement disagrees: a shorter retention or a longer
  scrape interval.

## 13. Architectural decisions and their reasons

- **One free tool per need, chosen by footprint**, because a game must
  fit a laptop next to the database it watches, and one well-built brick
  per need beats several half-built ones. Research may list three
  candidates; one is built.
- **Prometheus, `postgres_exporter`, Grafana with its own alerting,
  PostgreSQL file logs read by pgBadger**: the usual free stack, as in
  the owner's reference setup. No log aggregator, since pgBadger on files
  covers v0.2's log analysis at a fraction of the cost.
- **Per-node health from a script inside each node, no Docker socket**:
  the socket is root on the host, and the player side must never reach
  it. Rejected: cAdvisor and anything mounting the socket or the host.
- **The node-health script mounted as configs at deploy, as companion
  material of `prometheus`**: no image has to carry it, so no shared
  base image is needed and the v0.1 images need no change for it; it
  runs exactly when there is a metrics store to read it; and it is
  versioned, documented and faulted with the brick that uses it.
  Rejected: a new kind of brick with no node of its own; GM tooling
  outside the catalog (no version for a fault to name); baking it into
  every image (every brick image changed for one script).
- **No shared base image**: its one strong reason was carrying the
  health service. A base image sits outside the brick format (no
  definition, version or pin of its own), a change to it would rebuild
  and bump every brick, and bricks built from the same `debian:13-slim`
  already share that layer.
- **Every new brick a full node**, so players can investigate and fix
  the monitoring tools like any other node, with validators and sealed
  checks. Rejected: thin wrappers of upstream images without a shell,
  which would make every monitoring fault report-only. Prometheus and
  Grafana keep separate nodes.
- **A web front on the bastion rather than SSH forwarding**: the bastion
  stays the only way in, players with little programming experience need
  no tunnels, and the documentation website planned for v0.6 builds on
  it. Ports published by their own nodes are rejected: the routing mesh
  opens them on every host, bypassing the bastion.
- **One tools password** for the web front and Grafana's administrator,
  separate from the bastion password, so one leaked password does not
  open everything; a fixed administrator password per game makes a
  default-password fault meaningless.
- **Tooling expectations outside the faults**: under-tooling is a
  judgement about the customer, not a defect with a sealed check.
  Rejected: recording expectations only in the GM's notes, or only as
  issues.
- **Faults and scenarios never bump; bricks always do**: bricks are what
  images and pins depend on; a fault or scenario version never decided
  anything, and git history records their changes.
- **Version lists, not ranges, in `applies_to`**: a fault must be tried
  on every brick version it claims.
- **Evidence says where it is run, and every time is UTC**: v0.2 puts
  evidence in web interfaces and reports, and Grafana would otherwise
  show the browser's local time.

## 14. Definition of done

v0.1's checks still apply, extended:

1. The v0.2 scenario exists as a complete scenario folder, reviewed by
   the owner; every brick it uses passes the format skill's `docs/gm.md`
   check, `prometheus`'s covering the node-health script.
2. A full game runs on the `laptop` playground (2 CPU / 4G / 8G) from
   setup through hand-over, with `gmctl fit` passing, images counted.
3. **Footprint, measured.** `docker stats` samples every node at rest
   after hand-over, during a Grafana dashboard load and during a pgBadger
   run; `docker system df -v` gives the images' sizes and each volume's

## 15. Left for the build

The spec takes no position on these; the build settles or verifies each
and records what it found.

- Swarm refuses an empty config, while an s6 service folder uses empty
  files (`dependencies.d/base`, `contents.d/<service>`): the mounted
  versions need non-empty content.
- Mounting configs into an s6 service folder that the read-only image
  does not have.
- Reading the node's cgroup v2 files inside a Swarm container.
- Which unprivileged account the node-health script and its listener run
  as, and whether `s6-svstat` reads the services' status as that
  account; root only if it cannot.
- The web front's reverse proxy; Grafana's and Prometheus' sub-path
  settings; the web front not passing its `Authorization` header on to
  Grafana.
- Who creates the exporter's monitoring role (the data load or a
  start-up step) and how its password reaches the database.
- What the `prometheus`, `grafana` and `postgres-exporter` validators
  check, and the names of their `sudo` wrappers.
- The fixed port of the node-health listener.

## 16. Deferred items and remaining questions

Consciously left open; none blocks v0.2.

- **Backup tooling** (pgBackRest and the like) and its fault families
  (a wrong backup configuration, a restore that succeeds while
  integration fails, a restore that fails): backups were a founding
  example, yet no version has been chosen for them.
- **Network layout and network faults** (segmentation, exposure through
  the routing mesh, a management network) beyond v0.2's single network.
- **Multi-host swarms and a registry**: whether the first release still
  runs on one host once load and the full pipeline arrive.
- **Aging**: the default technique per fault (pre-aging, forged history,
  time compression), and where aging and the solvability probe enter the
  roadmap.
- **How many faults** per scenario, how many covered by issues, what
  difficulty means, whether an issue may be a false alarm; a deliberate
  masking pair of faults waits for this.
- **Report-only database nodes**: a non-superuser role there, or accept
  the `ALTER SYSTEM` gap.
- The other open items carried from v0.1 stand unchanged: further steps
  as scripts for generated scenarios; whether there is no project-wide
  machine check; the promotion of scenario-only bricks and faults;
  starter documentation as a fault; seeded variation; the brief's
  format; preparation time; recording player actions; the language of
  player-facing material; scores and saved feedback; a lighter record of
  intent; the vocabulary; unverified platform details (numeric-only
  owner ids in config mounts, the cross-host registry pattern, SSH Docker
  endpoints on Windows or macOS); the technologies of the first
  release's other roles.
- Fixed at consolidation by the spec writer, for the owner to revisit:
  the web front's default port (8080); Prometheus' admin and lifecycle
  endpoints left disabled, reloads going through the `sudo` wrapper; and
  the rule that players must not change Grafana's users or the
  administrator's password (access model).
