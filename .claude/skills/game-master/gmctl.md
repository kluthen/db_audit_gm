# `gmctl` for the GM — command reference

Every call the [GM skill](SKILL.md) makes, as built in v0.2. Run from the
repository root. Each subcommand takes `<scenario-dir> --playground
<name>`, prints a readable result, and exits non-zero on failure; `gmctl
<subcommand> --help` is the authority when this page and the tool
disagree. Fixed by captures W2-A, W2-C, W3-A and W3-B in
`specs/versions/v0.1/wave-log.md` (master spec 11); v0.2 changes the
secrets (generated by kind, capture W1 item 7 in
`specs/versions/v0.2/wave-log.md`), the network's name, the nodes'
time zone, the mounted companion material, the parameter faults and
`fit`'s images on the disk (v0.2 master spec 6.3, 6.4 and 8; capture W1
items 2, 4 and 8; spec D102), and the bastion's second published port, for
the web front (capture W2-C; spec D103). v0.2 adds no subcommand: the
monitoring tools and PostgreSQL's file logs are read through `exec`
(captures W2-B, W3-C and W3-D).

## Stages

`state.yaml` in `local/<pg>/` records, in order: `fitted`, `rendered`,
`deployed`, `data-loaded`, `injected`, `load-started`, `handed-over`,
`final-answer`, `feedback-given`, `torn-down`; or `failed`, with
`failure: {stage, reason, at}` (the stage it was working towards).
`gmctl` records every stage up to `load-started`, and `torn-down`; the GM
records the other three with `status --set`. Only a game with scheduler
nodes reaches `load-started` (v0.3 master spec 8, D157); a game with none
goes from `injected` to `handed-over`. From `start-load` on nothing sets
`failed`: a scheduler that does not start, a failed planting or a failed
early check is recorded in its own record (`load`, `plantings`,
`early_check`), tears nothing down, and heads `status` (master spec 8.7;
capture W2 in `specs/versions/v0.3/wave-log.md`). A `teardown` that leaves nothing labelled also
writes the teardown record, `teardown: {stage, reason, at}`: the last
stage reached, the `--reason` text (or `null`) and the time. Only the
first one writes it (a later teardown leaves it as it is); a failed game
keeps stage `failed` and its failure beside it. A new game has no record,
and a stage or failure recorded after it (a retried `deploy`) clears it.
The teardown a failed step runs itself writes none.

## Commands

| Command | Allowed at | Records | Exit |
|---|---|---|---|
| `tools/gmctl status <dir> --playground <pg>` | any game | nothing | 0; 1 no game |
| `tools/gmctl fit <dir> --playground <pg> [--endpoint ssh://user@host] [--cpu N --memory SIZE --disk SIZE]` | no game, `fitted`, `rendered`, `failed` before deployment (same game id); `torn-down`, or `failed` after deployment with its teardown recorded (a new game id) | `fitted` | 0 fits; 1 does not fit, or refused (a deployed stage, or a failure after deployment not torn down: the message names the game, its stage and `gmctl teardown`, or `gmctl deploy` for a failed deploy; the playground's engine not reachable; an image missing on it, with its build command; these last two write nothing) |
| `tools/gmctl render <dir> --playground <pg> [--handover <UTC date and hour>]` | `fitted`, `rendered` | `rendered`; the `timeline` in `implementation.yaml` | 0; 1 refused (no `--handover` with scheduler nodes, a hand-over not in the future or not a whole hour, the scenario changed since `fit`) |
| `tools/gmctl deploy <dir> --playground <pg> [--init-swarm] [--timeout SECONDS]` | `rendered`, or `failed` in deploy | `deployed` | 0; 1 refused or failed |
| `tools/gmctl load-data <dir> --playground <pg> [--timeout SECONDS]` | `deployed` (later deployed stages: no-op, exit 0) | `data-loaded` | 0; 1 refused or failed |
| `tools/gmctl inject <dir> --playground <pg> [--timeout SECONDS]` | `data-loaded`, `injected` (a replay) | `injected`; every instance's planting (`plantings`); with scheduler nodes only the instances due at T0 are planted | 0; 1 refused (at `load-started`: re-plant one instance with `--at now`) or failed |
| `tools/gmctl start-load <dir> --playground <pg>` | `injected`, with scheduler nodes | each attempt in `load`; T0 and `load-started` once every scheduler runs; the early check's host timer | 0 started; 1 refused (no scheduler node: `game <id> has no scheduler node, so it has no aging and no load to start (D157)`; the load already started; once handed over) or a scheduler did not start (recorded, nothing torn down, the stage stays `injected`: fix it and run it again, or tear the game down) |
| `tools/gmctl inject <dir> --playground <pg> --at <YYYY-MM-DDTHH:MMZ>\|now --instance <id>` | `load-started` | `plantings.<id>`: its host timer, or its attempt and, on success, `planted_at` | 0 scheduled or planted; 1 refused (not a `state` instance, a T0 instance (master spec 8.5), an instant not in the future or at or after the planned hand-over, an instant for an instance already planted, at or after hand-over) or the planting failed (recorded, nothing torn down, the stage unchanged) |
| `tools/gmctl check <dir> --playground <pg> --early-check` | `load-started` (the host timer runs it; the GM may run it again) | `early_check.result`; the outages; the earliest hand-over | 0 passed; 1 failed (recorded, nothing torn down); 2 refused (no scheduler node, another stage) |
| `tools/gmctl check <dir> --playground <pg> --handover-check` | `load-started`; `injected` with no scheduler node | a record in `handover_checks`; the outages; the earliest hand-over | 0 passed; 1 failed; 3 failed only on too-soon readings (wait the longest remaining window, then run it again); 2 refused |
| `tools/gmctl status <dir> --playground <pg> --set handed-over` | `load-started`, the earliest hand-over reached and the last hand-over check passed at or after it; with no scheduler node, `injected` and the last hand-over check passed | `handed-over` | 0; 1 refused (the condition not met, and for the earliest hand-over when it falls) |
| `printf '%s\n' 'cat ~/report.md' \| tools/gmctl exec <dir> --playground <pg> --node <bastion> --user player` | any deployed stage | nothing | the script's own; 125 could not start |
| `printf '%s\n' '<script>' \| tools/gmctl exec <dir> --playground <pg> --node <node> --user <user> [--env KEY=VALUE]` | any deployed stage | nothing | the script's own; 125 could not start |
| `tools/gmctl status <dir> --playground <pg> --set final-answer` | `handed-over` | `final-answer` | 0; 1 refused |
| `tools/gmctl validate <dir> --playground <pg>` | any deployed stage | nothing | 0 green; 1 red; 2 error or refused |
| `tools/gmctl check <dir> --playground <pg>` | `injected` and later deployed stages | nothing | 0 all fixed; 1 any present (none errored); 3 any too soon to tell (none errored or present: wait the longest remaining window, then run it again); 2 any error or refused |
| `tools/gmctl logs <dir> --playground <pg> --node <node> [--tail N]` | any game (useful while its services exist) | nothing | Docker's (`docker service logs`); 1 no game. A PostgreSQL node's shows sshd and the server's start-up only when its seed sets `logging_collector = on` (every v0.2 seed): its server log is then in files, read through `exec`; without the collector, the whole server log is here |
| `tools/gmctl status <dir> --playground <pg> --set feedback-given` | `final-answer` | `feedback-given` | 0; 1 refused |
| `tools/gmctl teardown <dir> --playground <pg> [--reason TEXT]` | any game (idempotent) | `torn-down` (a failed game stays `failed`), and the first time the teardown record, with the reason | 0; 1 leftovers (nothing recorded), or an empty reason (nothing removed) |

The deployed stages are `deployed` to `feedback-given`. `status --set` on
the stage the game is already at prints `Already at stage <stage>:
nothing changed.` and exits 0. `logs --follow` exists but blocks: the GM
does not use it.

`exec` streams its standard input into `sh -s` in the node's container,
as `--user` (any account the node has: `root`, `postgres`, `player`,
`prometheus`, `exporter`, `grafana`). `--env` (repeatable) sets a variable
for the script; its values show in the host's process list, so it carries
only values that are not secret (a PromQL query, an API path), never a
password or key. The GM's reads, one per tool, are in the skill's
[Operating the nodes and the monitoring tools](SKILL.md#operating-the-nodes-and-the-monitoring-tools).

## What the output looks like

- **`fit`**: the capacity lines, then `Result: fits. Game id <id>.` or
  `Result: does not fit; nothing deployed.` with one line per problem.
  `fit` reads the images from the playground's engine, so the engine
  must answer. Before the disk line, `images on <engine>: <image>
  <size>, ...; <n> layers, <k> shared, each counted once: <size>`; the
  disk line is `disk: reservations <r> + images <i> + headroom <h> =
  <total> of <disk>` (headroom 10 % of the declared disk). A layer
  several images hold (the `debian:13-slim` base) counts once. A missing
  image is refused as `image(s) not on <engine>: <image> (build it:
  docker build -t <image> bricks/<id>); ...; then gmctl fit again`
  (`docker -H <endpoint> build ...` for a remote engine); an engine that
  does not answer as `the engine <engine> is not reachable: <Docker's
  message>. ...`. An incomplete scenario: the list of missing items,
  then `refused`.
- **`render`**: `Game <id>: rendered.`, the stack file, each node's
  envelope file, then each node's own config of a mounted item
  (`mounted/<item>/<node>.conf`), then each seed file it rewrites
  (`rendered/<node>/<file>`), and `Stage rendered.` With scheduler nodes
  (v0.3 master spec 8.3; capture W2 item 1 in
  `specs/versions/v0.3/wave-log.md`) `--handover 2026-10-27T14:00Z` (or
  `...T14:00:00Z`, a whole UTC hour, in the future) is required: render
  prints `planned hand-over <instant>, shift <+N>, customer's time zone
  UTC+N (Etc/GMT-N)`, and records under `implementation.yaml`'s
  `timeline` the planned and designed hand-overs, the shift (between -11
  and +12), the customer's time zone, the game's seed (kept by a
  re-render, new after a refit), the aging minimum and every fault
  instance's planting moment and minimum. A planned hand-over too soon
  for the aging is not refused: one `warning:` line gives the earliest
  hand-over the game could have if the load started now. Each
  scheduler's `schedule.yaml` (with the seed; shapes per UTC weekday;
  timeline moments as UTC instants, `T0` as the render time) and
  `jobs.yaml` (every job's time shifted into UTC; a job with
  `timezone_offset: N` keeps its time in the zone `Etc/GMT∓M`, M the
  shift plus N wrapped into UTC-12..UTC+14) are rendered there, as are
  the bastion's files holding `{{customer_timezone}}`, filled with
  `UTC+2 (Etc/GMT-2)`. A scenario with no scheduler node renders without
  `--handover` and shifts nothing; given one, only the planned hand-over
  is recorded. Each seed config is mounted with its brick's `seed.modes`
  mode (`schedule.yaml` `0400`), `0444` otherwise, and a directory seed
  entry (`builders/`) as one config per file. Every node gets, after
  `TZ=UTC`, `GM_WRITE_POLICY` (its `write_policy`) and
  `GM_WRITE_OVERRIDES` (its `write_overrides`, sorted, space-separated,
  `""` when none; W1 item 5). Each role a scheduler's `schedule.yaml`
  names gets a password secret `role_<role>_password`, mounted root-only
  (`0400`) at `/opt/gm/secrets/` in each scheduler node naming it; a
  brick secret with `only_with_role` (the lookup role's
  `pgbouncer_lookup_password`, `pooler`) exists only when a node of the
  topology has that role. Parameter faults
  are planted here, before anything is derived from the parameters:
  each one's changes apply to its target node's parameters, so a node a
  fault leaves out of a node-map (the `prometheus` node's `node_health`)
  gets none of the material mounted from it, and a service left out of
  an entry is absent from that node's config. The
  mounted files and each receiving node's config are root-owned,
  read-only configs `deploy` creates with the others. A web-routes
  parameter reaches its node as `GM_<NAME>`, `name=node:port` tokens
  sorted by name (`""` when empty); a node-map parameter never as
  `GM_*`. A fault change that would plant nothing (an entry or a service
  not in the map) refuses `fit` and `render`.
- **`deploy`**: `Game <id>: deployed on <endpoint>.`, the credentials
  directory (never printed), the services healthy, then one line per
  published port: `node <bastion>: port <port> on the swarm host
  (container port <target>)`, target 22 for SSH and, with a web
  interface, 8080 for the web front; `Stage deployed.` It generates the secrets the
  bricks declare, fresh at each deploy: a password writes `<name>` (16
  characters when players type it, `handed_over`, else 32); a key pair
  (ed25519, no passphrase) writes `<pair>` and `<pair>.pub`. Every node
  runs with `TZ=UTC`, on the one network `<id>_<network name>`.
- **`load-data`**: one line per node's data file, `<node> <file> (psql as
  postgres): ok|exit N`, then, in a game with scheduler nodes, one per
  database node, `<node> passwords of <roles> (psql as postgres)`: each
  application role a schedule names gets its password from its secret
  (`role_<role>_password`) once the data has created it, on the database
  node the connection targets (every database node for a pooler target),
  sent as a SCRAM verifier with statement logging off, so no log holds
  it; a role the data did not create fails the step. The summary lists
  the files and `<node>: password set from its secret for role(s) ...`.
- **A failed setup step** (`deploy`, `load-data`, `inject`): `setup failed
  before stage <stage>: <reason>`, the teardown it ran, then `Recorded in
  state.yaml (stage failed).`
- **`inject`**: one line per script, `<instance> <script> (<node>, as
  <user>): ok|exit N`, then the script's output indented 4 spaces; the
  summary names each fault it ran nothing for, `<instance>: seed-file
  fault, planted by the seed files; nothing to run` or `<instance>:
  parameter fault, planted at rendering; nothing to run`. Spoilers: keep
  it from the players.
- **`start-load`**: `Game <id>: starting the load at <instant>.`, one
  line per scheduler node (`running since <instant>` or `FAILED:
  <reason>`), then `Load started: T0 <instant>. Stage load-started.`, the
  early check's time and timer, and, for every instance planted later,
  the `inject --at` command that plants it at its planned instant (`--at
  now` once that instant has passed): run each one. On each scheduler it
  writes the load-started marker holding T0, restarts the scheduler and
  waits up to 60 s for it to read running; T0 is the moment `start-load`
  began, the same on every node. The early check runs halfway through
  the aging minimum, or once every fixed-time operation due before the
  earliest hand-over has run once (plus 10 minutes), and no later than
  an hour before the earliest hand-over (master spec 8.5).
- **`inject --at`**: with an instant, `the planting of <id> is scheduled
  at <instant> (timer <unit>)`; a new instant replaces the timer. With
  `now`, the instance's scripts run as `inject` runs them, then `<id>
  planted at <instant>.`, or `FAILED: <reason>` and how to re-plant. The
  host timers are persistent systemd user units on the host running
  `gmctl`, `~/.config/systemd/user/dbagm-<id>_<action>.{timer,service}`
  (`plant-<instance>`, `early-check`): an action due while the host was
  down runs when it is back, first waiting up to 10 minutes for the
  game's nodes to run. A timer's run on a playground holding another
  game, or a torn down one, does nothing. `teardown` removes the game's
  timers before anything else.
- **`validate`**: each validator's lines under `<node>:` (`GREEN: ...`,
  or `RED <rule>: ...` lines, or `ERROR: ...`), ending `Validators of game
  <id>: <node> green|red|error, ...`.
- **`check`**: one line per fault instance, `<instance> <fault-id>:
  fixed|present|error — <reason>`, or, for a check that cannot tell yet,
  `<instance> <fault-id>: too-soon — <N> s of the window remain: <reason>`
  (the check judges a window that has not elapsed since the last change;
  wait N seconds, or report the fault as undetermined in the feedback);
  no summary line. A check on a Grafana node judges Grafana's live state
  through its API, not only the files. A check on a PostgreSQL node
  connects as the GM check role `gm_check`, inside the GM's reserve, so an
  exhausted `max_connections` does not lock it out; players see its
  sessions in the server log and `pg_stat_activity`.
- **`check --early-check`, `check --handover-check`** (master spec 8.5):
  the sealed check of every fault planted so far, passing when it exits
  as the answer key's `at_handover` says (1, present); in a game with
  scheduler nodes, every scheduler running, every current stream key with
  a line in the last complete minute, and every fixed-time operation due
  more than 10 minutes ago run once; every node healthy; the outages so
  far, recorded (never a failure on their own: the GM judges them). At the
  early check an instance due later is listed, not a failure, and a "too
  soon to tell" reading is recorded; at the hand-over check both fail it.
  A missed or failed planting fails both. A game with no scheduler node
  has no early check, and its hand-over check judges the faults and the
  nodes only. Lines per fault and per scheduler, then `<Early|Hand-over>
  check of game <id>: passed.` or `FAILED, <n> failure(s):` and each one.
- **`status`**: first, every unresolved failure and the outages:
  `FAILED start-load ...` (T0 not recorded), `FAILED|MISSED|UNSCHEDULED
  planting: ...` with the `inject --at now` that plants it, `FAILED early
  check ...` (until a hand-over check passes), `FAILED hand-over check
  ...`, `OUTAGES: <n> min lost in <k> period(s) ...` (`at least` when
  Swarm's task history of a node may have been pruned) with one line per
  period, `OUTAGES NOT READ ...`: tell the initiator of any before
  anything else. Then game id, playground and endpoint, stage (for a failed
  game, the last stage reached), the failure if any, the teardown record
  if any (`torn down: at <at>, from stage <stage>: <reason>`, or `no
  reason given`), the history, `network: <id>_<network name>`, and for a
  deployed game `secrets: <dir>/ (mode 0600, not printed)` followed by
  one line per file, indented 4 spaces: `<file>: password`, `<file>:
  password, handed over`, `<pair>: private key of pair <pair>` or
  `<pair>.pub: public key of pair <pair>`; `tools_password` only when the
  game has a web front (RG-3). In a game that ages, then: `aging: T0 <t0>;
  ran <time> (elapsed less the lost time) of the <minimum> minimum`, `lost
  time: <n> min`, `earliest hand-over: <instant> (reached | in <time> |
  provisional, waiting for the planting of <id>)` (the later of T0 plus
  the aging minimum and each fault's own minimum since its planting,
  moved later by the lost time beyond 30 minutes), the planned hand-over
  with the shift and the customer's time zone, each planting, and the
  early check; in every game, the last hand-over check. At `load-started`
  `status` reads the outages again from the schedulers' per-minute
  summaries and the nodes' task history.
- **`teardown`**: `Teardown of game <id>: removed ...; nothing carrying
  its label is left.` (`... nothing carrying its label was left.` when
  there was nothing to remove), then, when the game had host timers,
  `Host timers removed: <units>; none of the game's systemd units is
  left.`, then, the first time, `Recorded in state.yaml: torn down at
  <at>, from stage <stage>: <reason>.`; a later teardown given a reason
  says the record was left unchanged. Leftovers (a timer unit included):
  the list and exit 1, nothing recorded.

## Files of the local implementation the GM reads

In `scenarios/<id>/local/<pg>/` (git-ignored; never edit by hand):

- `playground.yaml`: `docker_endpoint` (`null` for the local engine) and
  the declared capacity;
- `implementation.yaml`: `game_id`, and per node `published_ports`
  (`[{target, published, mode}]`; only the bastion publishes ports: target
  22, SSH, and, when the topology has a web interface, target 8080, the
  web front);
- `state.yaml`: through `gmctl status`;
- `secrets/`: one file per secret the bricks declare (mode 0600; never
  print one anywhere but the hand-over). `gmctl status` lists them; the
  ones marked `handed over` are typed by players: `player_password`, the
  bastion password, and, once a topology declares it, `tools_password`
  (handed over only when the web front runs, spec D103). They stay there
  for the whole game, so a restarted GM hands them over again from them.
