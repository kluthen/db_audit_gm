# Folder layouts — scenario, brick, fault, purpose, domain

Version v0.5, expected to evolve as games are played. Source: v0.1
master spec sections 6.1, 7 and 8, v0.2 master spec 6 (capture W1 of
`specs/versions/v0.2/wave-log.md`), v0.3 master spec 6 and 7.1
(capture W1 of `specs/versions/v0.3/wave-log.md`) and v0.4 master spec
6, 7.1 and 7.2 (capture W1 of `specs/versions/v0.4/wave-log.md`, items 0,
5 to 8) and v0.5 master spec 6, 7.2, 8.4 and 8.5 with `specs/formats.md`
"Scenario", "Purpose definition" and "Domain" (capture W1 of
`specs/versions/v0.5/wave-log.md`, items 2, 5 and 7). Every entry is
required unless it says *optional*. YAML for structured content, Markdown
for prose.

## Scenario folder — `scenarios/<scenario-id>/`

```
<scenario-id>/
  README.md             the scenario document, generated (scenario-document skill)
  scenario.yaml         authoritative manifest            (template: scenario.yaml)
  brief.md              the initiator's inputs as given; may say "hand-written, no brief"
  player/               the starter pack, shipped to the bastion
    README.md           topology, node names, rules, DO NOT TAMPER list,
                        how to run the validator
    story.md            the customer's background
    issues.md           the issues given, each with its expected resolution
                        (may say there are none)
    data-policy.md      optional: with governance: only (v0.4), the company's
                        data policy, mapped to the bastion's optional seed file
                        data-policy.md
    partners.md         optional: with third_parties: only (v0.5), one entry per
                        partner (each third_parties entry's player_doc), mapped
                        to the bastion's optional seed file partners.md
    data-register.md    optional: with governance.register (v0.5; required with
                        domains:), the data register handout, generated by the
                        data-register skill, mapped to the bastion's optional
                        seed file data-register.md; absent when a planted
                        register fault is its absence
  gm/                   SEALED: never shipped to any node
    answer-key.yaml     authoritative answer key          (template: answer-key.yaml)
    notes.md            explanations the GM draws on for feedback
    data-register.yaml  optional: with governance.register (v0.5), the true
                        register, generated by the data-register skill, never
                        edited by hand; opens with generated_from:
  composition.yaml      optional: with domains: only (v0.5), required there; the
                        composition record, written by the GM (template:
                        composition.yaml)
  merge.yaml            optional: with domains:, when two profiles collided
                        (v0.5); the merge's resolutions gmctl compose reads
                        (template: merge.yaml)
  compose/<node>/       optional: with domains: (v0.5), the scenario layer gmctl
                        compose reads for each scheduler or api node it writes:
                        the purposes' material the GM adds, and each scheduler
                        node's intensity and timeline (never in a fragment);
                        laid out as that node's files. Kept apart from
                        nodes/<node>/, the output, so a rerun reproduces it
  nodes/<node>/         scenario-specific files per node (seed files), delivered
                        as Swarm configs; one folder per node with seed files.
                        A scheduler node's (brick `scheduler`): queries.yaml,
                        jobs.yaml, schedule.yaml, and optionally builders/, a
                        folder of files (no subfolder), in scenario time
                        (templates: queries.yaml, schedule.yaml, jobs.yaml;
                        master spec 7.1, capture W1 item 7); from v0.4
                        (`scheduler` 0.2.0) optionally scripts/, a folder of
                        transformer scripts, as builders/ is.
                        From v0.5 (`scheduler` 0.3.0) its schedule.yaml may hold
                        http connections and its queries.yaml call keys.
                        A database node's (brick `postgres`): postgresql.conf,
                        pg_hba.conf and, optionally from v0.4 (`postgres`
                        0.4.0), crontab, postgres' crontab in scenario time.
                        An api node's (brick `api`, v0.5): api.yaml (template:
                        api.yaml), routes/ and db/, folders of endpoint files
                        (routes/<name>.py and db/<name>.py per endpoint).
                        With domains:, a scheduler node's and an api node's
                        files are gmctl compose's output: written from the
                        domains' fragments, the variant's profile, compose/<node>/
                        and merge.yaml, each entry carrying its provenance
                        comment; never edited by hand
  data/<node>.sql       restored-backup data, streamed into the node;
                        one per node that holds data
  data/classification.yaml
                        optional: with governance: only (v0.4), the domain's
                        classification copied in, where governance.classification
                        names it (template: classification.yaml)
  bricks/<brick-id>/    optional: bricks made solely for this scenario
  faults/<fault-id>/    optional: faults made solely for this scenario
  local/<playground>/   local implementations, one per playground; git-ignored,
                        written by the GM at deployment, never by hand
```

Rules:

- `scenario.yaml` and `gm/answer-key.yaml` are authoritative. `README.md`
  is generated from them and opens with a prominent warning that students
  and players should not read it. The starter pack does not carry the
  warning.
- Nothing under `gm/` reaches a node. Nothing under `player/` gives away a
  hidden fault or an answer.
- `player/issues.md` states the same issues as `scenario.yaml` `issues`,
  each with its expected resolution.
- Every file a node's `seed_files` names exists; every `data.file` exists.
- Catalog bricks and faults are referenced by id and pinned version, never
  copied in.
- A seed entry ending in `/` (`builders/`, `scripts/`) maps to a folder
  of the scenario holding at least one regular file, named
  `[A-Za-z0-9_][A-Za-z0-9_.-]*`, and no subfolder; each file is delivered
  as its own seed config under the brick's `seed.dir`. A scheduler node's
  `scripts/` holds the transformer scripts its repository's script keys
  name (`script: scripts/<file>:<function>`), each a Python file defining
  the function at its top level.
- A seed file the brick lists under `seed.optional` (`postgres`'
  `crontab`) may be left out of a node's `seed_files`; render then mounts
  nothing for it, and the brick tells by its absence.
- **The data register's two files** (v0.5): `player/data-register.md` and
  `gm/data-register.yaml` are generated by the GM's `data-register` skill
  from the domains' register fragments and classification, `governance:`,
  `composition.yaml`, the topology, the purposes, the third parties and the
  answer key; never edited by hand, regenerated rather than reconciled.
  Required of every scenario listing `domains:` (v0.4's shop scenario is
  exempt until it is next revised).
- **`gmctl compose`** (v0.5) writes each target node's files under
  `nodes/<node>/` (a scheduler node's `queries.yaml`, `schedule.yaml`,
  `jobs.yaml`, `builders/`, `scripts/`; an `api` node's `api.yaml`,
  `routes/`, `db/`) from the layers, lowest first: the domains'
  `producers/<node>/` (and each `producers/partners/<partner>/` onto the
  shared nodes), the variant's `variants/<variant>/producers/<node>/`, the
  scenario's `compose/<node>/`; `merge.yaml` resolves a conflict between
  two sources of one layer. `scenario.yaml`'s `seed_files` stay the GM's.
- **A database node's crontab** (`nodes/<node>/crontab`, v0.4 master spec
  7.2): `postgres`' crontab, installed once into the spool and run by the
  node's cron daemon, which runs only on a node seeding it. Written in
  scenario time: render shifts each entry's hour field to UTC. Every time
  field is in the subset render can shift (capture W1 item 0: minute any
  numeric form; hour `*` or a comma list of `n`, `a-b`, `*/s`, `a-b/s`
  within 0-23, never wrapping; day of month and month `*`; day of week `*`,
  or a number or list 0-6 only with a single-number hour); no `@` form.
  The baseline connects as a customer role, never as `postgres` by peer
  (a superuser: a fault): the file sets `PGPASSFILE=/run/gm-cron/pgpass`
  on a line of its own above its entries, and an entry runs `psql -X -w
  -h /run/postgresql -U <role> -d <database> ...` and appends its output
  to `/var/log/postgresql/cron/<job>.log` (`>> ... 2>&1`), one file per
  entry, named by its job (`[a-z0-9-]+`). No entry holds a password: the
  node's `crontab_roles` in `scenario.yaml` names every role its entries
  connect as, and deployment mounts their passwords.

## Brick folder — `bricks/<brick-id>/`

```
<brick-id>/
  brick.yaml            identity, footprint, knobs, access, runtime, snapshot
                        methods                                     (template: brick.yaml)
  Dockerfile            and its build context; the image carries no scenario content
  validator/            the public validator, POSIX shell
  docs/player.md        what the player may read about this kind of node
  docs/gm.md            the GM documentation, never shipped: the nine required
                        sections of D56, in order               (template: brick-gm.md)
  companion/            optional: the brick's own checks, scripts and tools, and
                        material the GM mounts into other nodes; brick.yaml
                        `companion` says what it provides and when to use it, and
                        `companion.mounted` lists the mounted items
```

Rules:

- A brick's folder holds one version, the `version` of its `brick.yaml`;
  any change in the folder bumps it, unless the new version is still
  unreleased (it folds in). Bumping it re-pins every scenario and fixture
  that pins the brick, in the same change.
- **Mounted material** (`companion.mounted`): every file's `source` is
  under `companion/`; in each receiving node its `target` is an absolute
  path, root-owned (0:0) and read-only (no write bit), so a protected
  file. The material changes no image and no other brick's folder. The
  receiving nodes are the keys of the item's `parameter` (a `node-map`
  parameter set on the mounting brick's node), and each one's brick
  declares `receives`, meeting the item's `requires`.
- **The per-node config** (`node_config`) the renderer writes for each
  receiving node is UTF-8 text, one `key=value` per line, never empty:

  ```
  node=db
  services=postgres sshd
  disk_reservation=2147483648
  volumes=/var/lib/postgresql/18/data /etc/postgresql /home/player /var/lib/gm-state /run
  ```

  `services`: the node's map entry, `default` expanded to its brick's
  `processes`; `disk_reservation`: the node's
  `resources.reservations.disk` in bytes; `volumes`: the in-container
  paths of its brick's `volumes`.

## Purpose folder — `purposes/<purpose-id>/` (from v0.4)

```
<purpose-id>/
  purpose.yaml          identity, parts, jobs, trace, invariants, data moved,
                        roles                                  (template: purpose.yaml)
  material/             what the GM copies into a scenario at design time, one
                        folder per part receiving material, each file named as
                        the scenario's own for that part's node, as a fragment:
    runner/             queries.yaml, jobs.yaml and schedule.yaml fragments;
                        scripts/ (optional), the transformer scripts
    consumer/           optional: the same, for a purpose with a consumer
    receiver/           optional: the same, the stub's repository and schedule
                        (a pushed obligation)
    source/, target/    optional: data.sql, the DDL, roles and grants appended to
                        that node's data file (foreign servers and procedures
                        included)
    api/<node>/         optional (v0.5): routes/ and db/, the endpoints the purpose
                        brings to a customer's api node, the layout of a domain's
                        producers/api/<node>/
    history.sql         optional (v0.5): a periodic purpose's past periods' outputs,
                        planted into the target before T0 (purpose.yaml history)
  checks/               one script per invariant
  gm.md                 what the purpose is for, how it goes wrong, feedback notes
```

Rules:

- The id is `[a-z][a-z0-9-]*`, the folder's name. A purpose has no
  `version` and never bumps: its material is copied into a scenario,
  which names it in `purposes:` for provenance and for the faults
  attached to it. Purposes are looked up in the catalog only.
- A **fragment** has the scenario file's top-level keys holding only the
  entries it adds: `queries:`; `jobs:`; for a schedule `connections:`,
  `streams:`, `shapes:`, never `intensity` or `timeline`, which are the
  scenario's. Material is written for the first v0.4 scenario's mapping
  (nodes `db`, `reporting`, `bi`, `crm`, `consumer`, `gateway`; databases
  `shop`, `reporting`); the GM adapts the names as it copies, as it
  adapts a domain's files.
- Every invariant's `check` is a file of `checks/`.
- From v0.5 a fragment may hold an `api.yaml`'s `endpoints:` and
  `connections:` entries (`material/api/<node>/`), a schedule's http
  connections and a repository's call keys. A purpose's own tables in a
  domain's database live in schema `ops`, never in `public`; every run
  writes one `ops.runs` row in the same transaction as its output.

## Domain folder — `domains/<domain-id>/` (from v0.4; composed domains from v0.5)

As `specs/formats.md` "Domain" lays it out (v29):

```
<domain-id>/
  domain.yaml               identity, the parts below, the purposes that fit
                                                               (template: domain.yaml)
  data/
    schema.sql              the business tables, roles and grants
    load.sql                the generated history ("last night's backup")
    <database>/schema.sql   from v0.5, a part declaring databases: one folder per
    <database>/load.sql       database, in place of the two files above
    derive.sql              from v0.5, optional: a derivation step the GM may
                              sanction (domain.yaml derive)
    keys.sql                from v0.5, optional, a core's: its key functions,
                              pg_temp.core_*                (template: keys.sql)
    coherence.yaml          from v0.5, optional: the post-load coherence queries
                                                               (template: coherence.yaml)
    classification.yaml     every classed column           (template: classification.yaml)
    register.yaml           from v0.5: the register fragment, one entry per
                              activity                     (template: register.yaml)
    governance.yaml         from v0.5, optional: the business's own rules, with
                              docs/policy.md (both or neither)
  producers/                the business's producer fragments
    <node>/                 from v0.5 (D344): the fragments for the scheduler node of
                              that name (queries.yaml, schedule.yaml, jobs.yaml,
                              builders/, scripts/); api, partners and public are
                              reserved names
    api/<node>/             from v0.5: an api node the domain owns: its api.yaml
                              fragment (D345; template: api.yaml), routes/ (the
                              endpoints), db/ (their database side)
    partners/<prefix>/      from v0.5: a partner's back-end fragments at its root,
                              its api.yaml, routes/ and db/, and optionally
                              data.sql, its tables and state in the partners'
                              database                     (template: partner-data.sql);
                              the owners' traffic, no business, is
                              partners/owners/ (D369; public/ is reserved, unused)
  variants/
    <variant>.yaml          from v0.5: a variant's manifest (a part: its own axes)
                                                               (template: variant.yaml)
    <variant>/producers/    from v0.5, optional: the variant's profile, overrides
                              only, laid out as producers/
  docs/gm.md                the business, its rules, its traps
  docs/policy.md            from v0.5, optional: the business's default data policy
```

Rules:

- The id is `[a-z][a-z0-9-]*`, the folder's name; no `version`, never
  bumps; looked up in the catalog only. In the one-domain form
  (`domain:`) it is a design-time source: the GM copies its files into a
  scenario, adapting them, and `scenario.yaml`'s `domain:` names it for
  provenance. From v0.5 a composed scenario's `domains:` names each with
  its `at:`; `gmctl compose` merges its producer fragments into the
  scenario, but its data files (`schema.sql`, `load.sql`, `keys.sql`,
  `derive.sql`, each partner's `data.sql`, `coherence.yaml`) are never
  copied: `load-data` reads them from the catalogue at every load. A
  static scenario needs none.
- `schema.sql` and `load.sql` follow the data-load contract below;
  copied into a scenario they make its data file, `schema.sql` first.
  `load.sql` may read the two `psql` variables the data load passes.
- `classification.yaml` classes columns `personal`, `customer-linked` or
  `internal`; a column with no entry is `internal`. A scenario with
  `governance:` copies it where `governance.classification` names it.
  From v0.5 a domain keys its columns `<table>.<column>`
  (`<schema>.<table>.<column>` outside `public`), without the database;
  the scenario's copy adds it.
- From v0.5 every table of the domain belongs to exactly one activity of
  `data/register.yaml`. A fragment carries no timeline, no intensity and
  no planted fault (the scenario's); a partner's misbehaviour comes with
  its fault's material, never the domain's. Each partner prefixes its
  keys, connections and tables (`xlab.`, `xlab_`).

## Fault folder — `faults/<fault-id>/`

```
<fault-id>/
  fault.yaml            definition                       (template: fault.yaml)
  inject/               material that plants the fault: *.sh scripts (state faults),
                        snippets for seed files (seed-file faults); none for a
                        parameter fault, whose fault.yaml holds its parameter_changes
  checks/fixed.sh       the sealed check
  checks/probe.md       the solvability probe description (descriptive only in v0.1)
  gm.md                 explanation the GM uses for feedback
```

## Script contracts (master spec 8.1)

- **Injection scripts** (`inject/*.sh`): POSIX shell, fed on stdin to
  `sh -s` inside the target container, run as root unless the fault says
  otherwise, with parameters as environment variables (`FAULT_<NAME>`).
  Idempotent. Exit 0 on success; any other code fails the setup.
- **The data load** (`data/<node>.sql`): SQL, not shell, streamed on stdin
  into `psql -X -q -v ON_ERROR_STOP=1 -d postgres` run as `postgres`
  inside the node's container (local peer authentication); the file
  creates its own databases and roles. It runs once per game: loading
  again once the data is in changes nothing. Any error fails the setup.
  From v0.4 it gets two `psql` variables: `customer_timezone`, the bare
  zone (`Etc/GMT-2`; `Etc/GMT` at a shift of 0), and
  `customer_utc_offset`, the customer's offset from UTC in whole hours,
  east positive, without `+` (`2`, `-5`, `0`), read as
  `:'customer_timezone'` and `:customer_utc_offset`; a file that ignores
  them loads as before. The loader reads a data file line by line, never
  parsing SQL: it counts as created a database for each `CREATE DATABASE
  <name>`, a role for each `CREATE ROLE <name>` or `CREATE USER <name>`,
  and `pg_cron` for `CREATE EXTENSION [IF NOT EXISTS] pg_cron`, keywords
  in any case at the start of a line after blanks, `<name>` unquoted
  `[a-z_][a-z0-9_]*`, lines starting with `--` skipped; a statement inside
  a `DO` body or a function is not seen. A role a data file creates
  carries no password: the data load sets the passwords of the roles a
  schedule or a `crontab_roles` names.
- **Sealed checks** (`checks/fixed.sh`): same delivery as injection
  scripts. Exit 0: the fault is no longer present in the effective live
  state; 1: still present; 3 (v0.3): too soon to tell, with the remaining
  window on the first output line; any other code: error. First output
  line: why, in one sentence the GM can reuse. A fix counts whichever path
  the player took. A behavioural check (the fault's
  `sealed_check.behavioural`) also gets its instance's window and
  threshold as `CHECK_WINDOW_SECONDS` and `CHECK_THRESHOLD`. From v0.4 a
  check judging a purpose's runs or triggers (the fault's
  `sealed_check.judges`) gets its instance's threshold as
  `CHECK_THRESHOLD` and the judged moment as `CHECK_SINCE`, a UTC instant
  `YYYY-MM-DDTHH:MM:SSZ`; the exit codes are unchanged.
- **Database checks** (v0.3 master spec 6.5): a check that queries
  PostgreSQL connects as the GM check role `gm_check`, inside the GM's
  connection reserve, as root through the root-only helper
  `/usr/local/lib/gm/check-psql -d <db> -Atq -v ON_ERROR_STOP=1`
  (`postgres` 0.3.0, capture W1 item 8); never as `dba` or an
  application role. Clients of the load connect as ordinary roles. From
  v0.4 a check comparing two instances reaches each as `gm_check`: from a
  scheduler node through `check-sql`, from a database node through
  `check-psql` with the other node's name (`postgres` 0.4.0; its form in
  the brick's `docs/gm.md`), the other node's seed `pg_hba.conf` admitting
  `gm_check` from the game network.
- **Public validator** (`validator/`): exit 0 green; 1 red, with one line
  per broken rule; any other code is an error.
