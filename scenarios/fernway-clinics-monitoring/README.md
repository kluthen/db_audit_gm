## 2. Background

Fernway runs four veterinary clinics and an online booking site on one
PostgreSQL database. After an outage nobody noticed for a morning, a
freelancer set up Prometheus, a PostgreSQL exporter and Grafana in April
(dashboards, alert rules, the alert list on the reception screen) and left
in June. Since then a Grafana restart went unseen, a 90-minute database
outage raised no service alert, and the query statistics panels have been
empty since May. Beatriz Lund, the practice manager who handles IT, asks for
an audit of the monitoring and of the database before the winter vaccination
campaign. The data file creates the roles fernway (owner of the database, no
login) and clinic_app (the booking site's login, with data rights on every
table; made superuser after the load, f7); the brick creates dba, the
players' superuser, and monitoring, the exporter's role.

### `f1`: `prometheus-scrape-target-missing` on `prometheus`, known

- **What is wrong**: Prometheus never scrapes the grafana node's node-health
  endpoint: the node-health job in /etc/prometheus/prometheus.yml lists
  bastion, db, prometheus and exporter on port 9110, not grafana:9110. The
  grafana node runs the node-health script and answers on its endpoint; only
  the scrape is missing.
- **Why it matters**: grafana's CPU, memory, disk and services are monitored
  nowhere: it is in no panel of the node-health dashboard and no alert can
  fire for it ("Scrape target down" only covers targets Prometheus knows).
  That is why its two restarts in September left no trace (issue I1). The
  dashboard looks complete because nothing on it says a node is missing.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `ui:prometheus` | Prometheus' targets page, /prometheus/targets | `open Status, Target health, and read the node-health job` | four node-health targets (bastion, db, prometheus, exporter) for five nodes in the topology; grafana:9110 is absent, not down |
| `ui:grafana` | the node-health dashboard, /grafana/d/node-health | `open the dashboard and read every panel's legend` | grafana appears in no panel, while bastion, db and prometheus do |
| `ui:grafana` | Grafana's alerting view, /grafana/alerting/list | `read the state of "Scrape target down"` | the rule stays Normal although grafana is never scraped; it cannot fire for a target Prometheus does not know |
| `node:prometheus` | /etc/prometheus/prometheus.yml | `ssh prometheus, then cat /etc/prometheus/prometheus.yml` | the node-health job's targets: 'bastion:9110', 'db:9110', 'prometheus:9110', 'exporter:9110'; no grafana |
| `node:prometheus` | grafana's node-health endpoint, read from the prometheus node | `ssh prometheus, then curl -s grafana:9110/metrics \| grep sample_age` | node_health_sample_age_seconds lines labelled node="grafana": the endpoint answers, only the scrape is missing |

Acceptable answers:

- **Diagnosis**: names grafana as never scraped for node health (its
  grafana:9110 target missing from the node-health job), tells a target
  absent (silence) from a target down, shows the endpoint answers, and notes
  that no alert can fire for the node; links it to the unseen restarts of
  I1.
- **Proposal**: add grafana:9110 to the node-health job and reload
  Prometheus (sudo gm-reload-prometheus); keep the target list in step with
  the topology and check the targets page after each change.
- **Fix**: Prometheus, in its live state after a reload, holds node-health
  samples for grafana (node_health_sample_age_seconds{node="grafana"}
  answers an instant query); the targets page shows grafana:9110 up and the
  other targets still scraped; grafana now appears on the node-health
  dashboard.

Sealed check: `faults/prometheus-scrape-target-missing/checks/fixed.sh`,
exit 1 at hand-over (0: fixed, 1: present, 3: too soon to tell). Reads
Prometheus' live state, not the file: a file edited but not reloaded reads
1, and so does a target added in the last few seconds, before its first
scrape (15 s); run the check again a little after the reload. Fixing it
does not touch f2 (the exporter's target stays down).

Interactions: none.

### `f2`: `prometheus-node-health-node-missing` on `prometheus`, hidden

- **What is wrong**: the exporter node has no node-health script: its entry
  was left out of the node_health map, so nothing was mounted into it
  (/opt/gm/node-health/ and /usr/local/lib/gm/node-health/ are absent) and
  its port 9110 refuses connections. Prometheus still lists exporter:9110
  among its node-health targets.
- **Why it matters**: the exporter node's CPU, memory, disk and services
  (the exporter itself included) are monitored nowhere: if the exporter
  stopped, only the PostgreSQL panels going empty would show it. The target
  has been down since April and "Scrape target down" has fired ever since;
  the customer learned to ignore it ("a leftover", story.md). An alert that
  always fires is still an alert.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `ui:prometheus` | Prometheus' targets page, /prometheus/targets | `open Status, Target health, and read the node-health job` | exporter:9110 down, with an error saying the connection was refused |
| `ui:grafana` | Grafana's alerting view, /grafana/alerting/list | `open Alerting, Alert rules, and read "Scrape target down"` | the rule firing for instance exporter:9110 (from about 2 minutes after the start) |
| `ui:grafana` | the node-health dashboard, /grafana/d/node-health | `open the dashboard and read every panel's legend` | exporter appears in no panel |
| `node:exporter` | the node's file system | `ssh exporter, then ls /opt/gm/node-health /usr/local/lib/gm/node-health` | No such file or directory for both, while every other node has them (ssh db, same command) |

Acceptable answers:

- **Diagnosis**: names the exporter node as running without the node-health
  script (target known and down, connection refused, nothing on the node),
  tells it apart from a node Prometheus does not scrape (f1), and says the
  firing alert is real, not noise to live with.
- **Proposal**: deploy the node-health script on the exporter node as on the
  others (its entry in the monitoring configuration, then a redeploy by
  whoever runs the platform); keep the target-down alert, which caught it,
  and act on alerts rather than learning to ignore them.

Sealed check:
`faults/prometheus-node-health-node-missing/checks/fixed.sh`, exit 1 at
hand-over (0: fixed, 1: present, 3: too soon to tell). Hidden; report or
propose only (the script and its configuration are mounted read-only by
the platform): it reads 1 for the whole game. Removing exporter:9110 from
prometheus.yml silences the alert but is not a fix: judge it as hiding the
problem.

### `f3`: `prometheus-node-health-service-missing` on `prometheus`, known

- **What is wrong**: the node-health script on db watches sshd only:
  postgres was left out of db's service list (/opt/gm/node-health/node.conf
  has services=sshd), so no node_health_service_up series exists for
  postgres on db.
- **Why it matters**: db shows healthy while PostgreSQL is down: "Service
  down on a node" evaluates node_health_service_up and has no postgres
  series to see go to 0. This alone explains why the October outage raised
  no service alert (issue I2); f5 explains it a second time. The one service
  that matters most is the one not watched.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `node:db` | /opt/gm/node-health/node.conf | `ssh db, then cat /opt/gm/node-health/node.conf` | services=sshd (on prometheus, the same file lists prometheus and sshd) |

| `ui:prometheus` | an instant query, /prometheus/query | `query node_health_service_up{node="db"}` | one series, service="sshd"; none for postgres |

Acceptable answers:

- **Diagnosis**: names postgres as missing from db's node-health service

- **Proposal**: add postgres to db's node-health service list (the

only (read-only material): it reads 1 for the whole game. I2 expects a
proposal, so 1 is the expected outcome.

### `f4`: `pg-stat-statements-not-preloaded` on `db`, known

- **What is wrong**: pg_stat_statements is not preloaded: in
  /etc/postgresql/postgresql.conf the shared_preload_libraries line is
  commented out ("off while chasing the May crash; to put back"). The
  extension exists in database postgres, but the server collects no
  statement statistics.
- **Why it matters**: the exporter's stat_statements collector fails, so the
  PostgreSQL dashboard's four statement panels stay empty while the exporter
  is connected (issue I3); without query statistics nobody can tell which
  queries make Monday mornings slow, and performance work turns into
  guessing.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `ui:grafana` | the PostgreSQL dashboard, /grafana/d/postgresql | `open the dashboard` | the four statement panels say No data, while "Exporter connected to PostgreSQL" is at 1 |
| `ui:prometheus` | an instant query, /prometheus/query | `query pg_scrape_collector_success{collector="stat_statements"}, then pg_stat_statements_calls_total` | the collector at 0, and no pg_stat_statements_calls_total series |
| `bastion` | psql from the bastion, database postgres | `psql -h db -d postgres -c 'SELECT * FROM pg_stat_statements LIMIT 1' -c 'SHOW shared_preload_libraries'` | "pg_stat_statements must be loaded via shared_preload_libraries"; the setting is empty |
| `node:db` | /etc/postgresql/postgresql.conf | `ssh db, then grep -n shared_preload_libraries /etc/postgresql/postgresql.conf` | the line commented out, with the comment about the May crash |

Acceptable answers:

- **Diagnosis**: names pg_stat_statements as installed but not loaded
  (missing from shared_preload_libraries), connects it to the empty panels
  and the failing collector, and says a reload is not enough.
- **Proposal**: put pg_stat_statements back into shared_preload_libraries
  (postgresql.conf, or ALTER SYSTEM) and restart PostgreSQL (sudo
  gm-restart-db), planned since it drops every connection; then read the
  costliest statements in the panels or the view.
- **Fix**: pg_stat_statements is in the shared_preload_libraries in effect
  (the server was restarted) and SELECT count(*) FROM pg_stat_statements
  succeeds in database postgres, by either path; the statement panels fill
  within about a minute and a half; the validator on db is still green.

Sealed check: `faults/pg-stat-statements-not-preloaded/checks/fixed.sh`,
exit 1 at hand-over (0: fixed, 1: present, 3: too soon to tell). A file
edited (or ALTER SYSTEM run) but not restarted reads 1. After
gm-restart-db it reads 0 at once; the panels lag by about 70 s.

### `f5`: `grafana-alert-for-too-long` on `grafana`, known

- **What is wrong**: the alert rule "Service down on a node" (uid
  gm-service-down) has a pending period (for) of 2h in
  /etc/grafana/provisioning/alerting/alert-rules.yaml; the other four rules
  wait 1m or 5m.
- **Why it matters**: a service must stay down for two hours before the
  alert fires: the 90-minute outage of I2 could never have raised it, even
  if the service were watched (f3), and any longer one is reported two hours
  late. A rule that cannot fire in time is no rule; on the reception screen
  it looks perfectly normal.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `ui:grafana` | Grafana's alerting view, /grafana/alerting/list | `open the rule "Service down on a node" (folder db_audit_gm) and read its details` | pending period 2h, against 1m or 5m for every other rule |

### `f6`: `pg-hba-trust-remote` on `db`, hidden

- **What is wrong**: pg_hba.conf on db has `host all all 0.0.0.0/0 trust`
  (commented "temporary, while setting up the monitoring (April)") before
  the monitoring role's line and the scram-sha-256 host line, so every TCP
  connection from any address is accepted without a password, for any role.
- **Why it matters**: anyone who reaches port 5432 logs in as any role (dba,
  postgres, clinic_app) without a password: full control of the clinics'
  data (owners' names, e-mails and phone numbers) and operating-system
  access as postgres. The lines after it never apply.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|

| `bastion` | the pg_hba_file_rules view | `psql -h db -c 'SELECT line_number, type, database, user_name, address, auth_method FROM pg_hba_file_rules'` | a host rule for 0.0.0.0 with auth_method trust, matched before the scram-sha-256 rules |

Acceptable answers:

### `f7`: `pg-role-superuser` on `db`, hidden

- **What is wrong**: the booking site's login role clinic_app is a
  superuser. It already holds the data rights it needs (SELECT, INSERT,
  UPDATE, DELETE on every table of clinic, USAGE on its sequences), so the
  attribute adds nothing the site uses.
- **Why it matters**: an SQL injection in the booking site or a leaked
  application password gives full control: every database, every setting,
  and operating-system commands as postgres (COPY ... TO PROGRAM). The data
  is personal (owners' contact details). Least privilege: data rights on its
  own database only.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `bastion` | the cluster's roles | `psql -h db -c '\du'` | clinic_app with the Superuser attribute, next to dba and postgres |
| `bastion` | the role's own rights on clinic | `psql -h db -d clinic -c '\dp'` | clinic_app already has arwd on every table, so it needs no superuser attribute |

Acceptable answers:

- **Diagnosis**: names clinic_app as a superuser it need not be, and the
  risk (a compromised site or password owns the whole server).
- **Proposal**: ALTER ROLE clinic_app NOSUPERUSER, keeping its grants on
  clinic; check that it can still read and write the tables (SET ROLE
  clinic_app; SELECT ...; RESET ROLE).
- **Fix**: clinic_app still exists, can log in, and is no longer a
  superuser; its data rights on clinic are intact. Dropping the role or
  revoking its grants breaks the booking site and is not acceptable.

Sealed check: `faults/pg-role-superuser/checks/fixed.sh`, exit 1 at
hand-over (0: fixed, 1: present, 3: too soon to tell). Hidden. The check
does not test the grants: when it reads 0, run \dp on clinic through gmctl
exec before accepting the fix.

### `f8`: `pg-table-autovacuum-off` on `db`, hidden

- **What is wrong**: autovacuum is disabled on the appointments table
  (storage parameter autovacuum_enabled=off), while the server-wide
  autovacuum setting is on and the validator is green on it.
- **Why it matters**: appointments changes all day (bookings, moves,
  cancellations, status updates): dead rows pile up (bloat, slower scans),
  statistics go stale (bad plans for the agenda's queries), and only the
  forced anti-wraparound vacuum would ever process it. The winter
  vaccination campaign makes it worse.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `bastion` | the table's options | `psql -h db -d clinic -c '\d+ appointments'` | Options: autovacuum_enabled=off |
| `bastion` | every table with storage parameters | `psql -h db -d clinic -c "SELECT relname, reloptions FROM pg_class WHERE relkind = 'r' AND reloptions IS NOT NULL"` | appointments \| {autovacuum_enabled=off} |

Acceptable answers:

- **Diagnosis**: names the table-level autovacuum_enabled=off on
  appointments and its consequences (bloat, stale statistics, wraparound
  protection left to the forced vacuum), noting that SHOW autovacuum says
  on.
- **Proposal**: ALTER TABLE appointments RESET (autovacuum_enabled), then
  VACUUM (ANALYZE) appointments; per-table thresholds if the table were too
  busy for the defaults, never off.
- **Fix**: appointments no longer has autovacuum_enabled set to false
  (reset, or set to on).

Sealed check: `faults/pg-table-autovacuum-off/checks/fixed.sh`, exit 1 at
hand-over (0: fixed, 1: present, 3: too soon to tell). Hidden; a manual
VACUUM alone does not change the check (the option stays off).
