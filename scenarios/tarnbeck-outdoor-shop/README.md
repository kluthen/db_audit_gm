## 2. Background

Tarnbeck Outdoor sells camping and hiking gear online. Its web shop
(checkout with a payment provider, the catalogue, the order pages, the
warehouse's packing and shipping, the carriers' delivery feed and a
close-of-day batch) writes into one PostgreSQL database through PgBouncer;
its back office (dashboards, a sales report, a nightly roll-up and the
accounting export) reads it directly. Prometheus, a PostgreSQL exporter and
Grafana were set up last year. The developer who built it left in the
summer; Ines Varga, the operations manager, asks for an audit after weeks of
lunchtime slowdowns, duplicated deliveries and an export that arrives late.
The data file creates the roles shop (owner of the database, no login),
shop_app (the web shop, through the pooler) and shop_reports (the back
office, straight to the database); the brick creates dba, the players'
superuser, monitoring, gm_check and pgbouncer_lookup.

### `f1`: `scheduler-query-error` on `producer`, hidden

- **What is wrong**: The web shop's catalog.lookup key fails at one call in
  ten: its third entry, the search by product code, compares products.id (an
  integer) with the text 'TB-' || lpad(code, 5, '0'), so PostgreSQL rejects it
  at every call with SQLSTATE 42883 (operator does not exist: integer = text).
  The code is in products.sku.
- **Why it matters**: Every product-code search ends on the shop's error
  page (the story's "error page now and then"), about twelve a minute at the
  noon peak, since the release; the application hides it behind a generic
  page, and the errors fill the application's log and the database's.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `node:producer` | the scheduler's log, error lines | `ssh producer, then grep 'error key=catalog.lookup ' /var/log/scheduler/scheduler.log \| tail` | sqlstate=42883 message="operator does not exist: integer = text ..." lines, every minute since last night |
| `node:producer` | the scheduler's log, per-minute key lines | `grep 'key=catalog.lookup ' /var/log/scheduler/scheduler.log \| tail` | errors= about a tenth of calls= in every minute |
| `node:producer` | the query repository | `cat /srv/scheduler/repository/queries.yaml` | catalog.lookup's third entry: WHERE id = 'TB-' \|\| lpad(%(code)s::text, 5, '0'), weight 1 of 10 |
| `node:db` | the PostgreSQL log | `ssh db, then grep -A1 'operator does not exist' /var/log/postgresql/postgresql-*.log \| tail` | ERROR and STATEMENT lines from user=shop_app, app=producer, with the search's SQL |
| `ui:prometheus` | the scheduler's error counter | `in Prometheus' graph, rate(scheduler_errors_total{key="catalog.lookup"}[5m])` | a steady error rate since the start, following the day's traffic (highest at noon) |

Acceptable answers:

- **Diagnosis**: names the product-code search of catalog.lookup as failing
  at every call, with SQLSTATE 42883 and its cause: the integer id compared
  with a text code (the code is the sku).
- **Proposal**: compare the sku: WHERE sku = 'TB-' || lpad(%(code)s::text,
  5, '0'), in queries.yaml, then sudo gm-reload-scheduler; test the query by
  hand first.
- **Fix**: the entry corrected in the loaded queries.yaml (sku compared, or
  any SQL that returns the product without error), reloaded with sudo
  gm-reload-scheduler, and the key's calls since that reload ending without a
  class 42 or 22 error. Removing the search entry also reads fixed; the GM
  weighs a search taken away from the shop.

Sealed check: `faults/scheduler-query-error/checks/fixed.sh`, exit 1 at
hand-over (0: fixed, 1: present, 3: too soon to tell). Right after a reload
of the producer it reads too soon (exit 3) for up to about 130 s, then at
most 70 s: run it again. Any reload of the producer restarts that wait, so a
fix of f3 or f5 puts f1 back to too soon for a minute or two.

Interactions: none.

Public validators the players cannot make green (reporting each is part of
the expected answer): none.

### `f2`: `scheduler-report-unbounded` on `consumer`, known

- **What is wrong**: The back office's reports.best-days report (each day's
  three biggest orders) reads and sorts the whole orders table at every run:
  SELECT * with row_number() over placed_at::date, and no bound on placed_at
  (its period was dropped). 300 000 rows at the backup and about 30 000 more a
  day; each run sorts them all and spills about 20 MB to temporary files at
  work_mem 4MB, to return three rows per day of history.
- **Why it matters**: The cost grows with the table (slower every week,
  issue I5), twenty runs an hour in office hours, each a full scan, a sort on
  disk and a burst of CPU on the database's single CPU; SELECT * ships every
  column of every order to the sort.

Evidence, as the `player` user (and `dba` in psql):

| Where | Source | How | Shows |
|---|---|---|---|
| `node:consumer` | the query repository | `ssh consumer, then cat /srv/scheduler/repository/queries.yaml` | reports.best-days with SELECT * and no WHERE on placed_at in the inner query |
| `node:consumer` | the scheduler's log, per-minute key lines | `grep 'key=reports.best-days ' /var/log/scheduler/scheduler.log \| tail` | p50_ms in the hundreds of milliseconds, where the other keys take a few |
| `bastion` | pg_stat_statements | `psql -d postgres -c 'SELECT calls, rows, mean_exec_time, temp_blks_written, query FROM pg_stat_statements ORDER BY temp_blks_written DESC LIMIT 5'` | the report first, temporary blocks written at every call, about 50 rows a call |
| `bastion` | the report's plan | `psql -d shop, then EXPLAIN (ANALYZE, BUFFERS) on the report's SQL` | Seq Scan on orders, then Sort Method: external merge Disk: about 20000kB |
| `node:db` | the PostgreSQL log | `ssh db, then grep 'temporary file' /var/log/postgresql/postgresql-*.log \| tail` | a temporary file of about 20 MB at every run, user=shop_reports, app=consumer |
| `report:pgbadger` | pgBadger's report, "Temporary Files" and "Slowest queries" | `ssh db, then pgbadger -o ~/pgbadger.html /var/log/postgresql/postgresql-*.log` | the report as the query writing the temporary files |
| `ui:grafana` | the PostgreSQL dashboard's query statistics panels | `open /grafana/, the PostgreSQL dashboard` | the report among the queries costing the most time |

Acceptable answers:

- **Diagnosis**: names the report as reading the whole orders table (no
  bound on placed_at), sorting all of it and spilling to temporary files, its
  cost growing with the table; notes SELECT *.
- **Proposal**: bound the report to its period, for example WHERE
  o.placed_at >= current_date - 7 in the inner query (orders_placed_at_idx
